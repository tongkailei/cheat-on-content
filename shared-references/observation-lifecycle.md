# 观察生命周期 / Observation Lifecycle

## 核心原则

rubric 是**工作台**，不是**博物馆**。

被新数据推翻或被吸收为正式维度的观察，**直接删掉**。不留"我曾经以为 X 但其实..."的考古层。git history 才是档案。

---

## 为什么不能堆叠观察？

内容创作领域，观察是**易错的、暂时的**：

- 今天有效的 pattern，明天可能被算法改变
- 平台规则变化会让旧观察失效
- 堆叠的观察会造成 cognitive load，增加决策负担

---

## 观察处理规则

### 规则 1：被推翻 → 删

```
观察："标题用疑问句能提升点击率"
来源：样本 #3, #7
状态：被样本 #12 推翻（疑问句标题 #12 点击率低于陈述句）

操作：直接删除，不留"曾经以为..."
理由：git history 会保留
```

### 规则 2：被验证 → 吸收入正式维度

```
观察："情绪共鸣维度和播放时长高度相关"
验证：样本 #5-#10 都支持这个结论
状态：足够 strong signal

操作：
1. 加入 rubric_notes.md 正式维度（如已有"情绪价值"维度，调整其权重）
2. 删除原始观察笔记
理由：已沉淀为规则，不需要作为临时观察存在
```

### 规则 3：新观察 → 短期保留

```
观察："视频前三秒有具体数字的钩子表现更好"
样本基础：样本 #8, #9 支持
confidence：low（只有 2 个样本）

操作：保留在 rubric_notes.md 的"观察笔记"区
等待：积累到 5 个样本后决定是验证还是删除
```

## 观察笔记模板

```markdown
## 观察笔记（Active）

| 观察 | 样本支持 | 置信度 | 状态 | 处理 |
|------|----------|--------|------|------|
| 标题用疑问句提升点击 | #3, #7 | medium | pending | 待验证 |
| 情绪共鸣维度关联播放时长 | #5-#10 | high | 验证中 | 拟吸收 |
| ... | ... | ... | ... | ... |

## 观察笔记（已处理）

（空——所有观察要么被验证吸收，要么被推翻删除）
```

## 拒绝场景

### ❌ 拒绝模式

**用户**：「把 rubric_notes.md 里所有历史观察都留着，加个时间戳分组就行」

**原因**：这违反了"工作台非博物馆"原则。堆叠的观察会：
- 制造认知负担
- 让决策变得缓慢
- 积累过时的、可能错误的 pattern

**正确做法**：定期清理观察笔记，被推翻的直接删除。

---

## 定期清理节奏

建议每完成 **5 次复盘** 后，做一次观察笔记清理：

1. 遍历所有 active 观察
2. 检查是否有新数据支持/推翻
3. 被推翻的 → 删除
4. 被验证的 → 吸收为正式维度
5. 仍pending的 → 继续保留

---

## Git History 是档案

如果担心删除后丢失，可以：

```bash
# 提交时留有意义的信息
git commit -m "chore: 删除被推翻的观察（疑问句标题假设）"
git commit -m "feat: 吸收'情绪共鸣→播放时长'为正式维度"
```

这样既保持工作台干净，又通过 git 保留了完整历史。
