# Cheat-Bump：Rubric 升级

用校准池数据更新评分公式，是最核心的迭代动作。

---

## 前置检查

1. **确认 .cheat-state.json 存在**
2. **确认校准池 ≥ 5 个样本**：读取 `predictions/` 中有完整 ## 复盘 的文件数
3. 如果 < 5，告知用户暂时不能 bump，需要继续积累

---

## 核心原则

**升级 = 全量重打**

- rubric 变了 → 所有校准池样本必须用新公式重新打分
- 新排序 vs 实际排序 → ≥4/5 一致才允许升级
- 拒绝"跳过重打直接换公式"

---

## Bump 流程

### Step 1：读取当前 Rubric

从 `rubric_notes.md` 读取当前 7 维和权重。

### Step 2：读取所有校准样本

读取 `predictions/` 中所有有 ## 复盘 数据的文件，提取：
- 各维度评分
- 实际播放量 bucket

### Step 3：分析偏差模式

统计：
- 哪些维度普遍高估/低估？
- 哪些维度和实际表现相关性最高/最低？
- 当前权重是否需要调整？

输出偏差分析报告：

```
📊 Rubric 偏差分析

维度 1-7 的预测偏差统计：
├ 钩子强度：低估 3 次，高估 2 次，平均偏差 +0.3
├ 观点冲击力：低估 1 次，高估 4 次，平均偏差 -0.5
├ ...

权重调整建议：
├ 观点冲击力：20% → 25%（与实际播放量相关性最高）
├ 结构节奏：10% → 5%（与实际播放量相关性最低）
└ ...
```

### Step 4：提出新 Rubric 方案

基于分析，提出新的评分维度/权重方案。

格式：

```markdown
## 新 Rubric 提案

### 调整内容
- <维度 A>：<旧权重> → <新权重>（理由：...）
- <维度 B>：新增（理由：...）
- <维度 C>：删除（理由：...）

### 预期效果
- 高估的维度权重降低
- 低估的维度权重提高
- 新增对预测有帮助的维度
```

### Step 5：全量重打验证

用新公式重打所有校准池样本，生成新排序。

### Step 6：对比验证

```
新排序 vs 实际排序对比：

| 样本 | 实际排名 | 新公式排名 | 一致？ |
|------|----------|------------|--------|
| 样本1 | L3       | L3         | ✅     |
| 样本2 | L2       | L3         | ❌     |
| 样本3 | L4       | L4         | ✅     |
| 样本4 | L2       | L2         | ✅     |
| 样本5 | L3       | L3         | ✅     |

一致率：4/5 = 80% ✅ 允许升级
```

**如果一致率 < 80%**：
→ 拒绝此次升级
→ 分析不一致的样本，找出问题
→ 调整新 rubric 方案，重新验证

### Step 7：用户确认

```
⚠️ Rubric 升级确认

新权重方案：
├ 钩子强度：20% → 25%
├ 观点冲击力：20% → 25%
├ 逻辑完整性：15%（不变）
├ 情绪价值：15%（不变）
├ 实用价值：10%（不变）
├ 结构节奏：10% → 5%
└ 预期管理：10%（不变）

验证结果：4/5 样本一致 ✅

确认升级？(y/n)
```

### Step 8：执行升级

- 更新 `rubric_notes.md`
- 更新 `.cheat-state.json` 的 `lastBumpAt`
- 在 `CHANGELOG.md` 记录此次升级

```
└ ...

```

---

## 拒绝场景

以下情况**拒绝执行 bump**：

1. 校准池 < 5 个样本
2. 一致率 < 80%
3. 用户要求"跳过重打直接换"
4. 用户试图降低 threshold（4/5 是底线）

---

## 注意事项

- bump 是不可逆的（旧 rubric 可以从 git history 恢复）
- 建议每次 bump 后在 CHANGELOG.md 记录，方便回溯
- 新rubric需要再积累 5+ 样本才能再次 bump
